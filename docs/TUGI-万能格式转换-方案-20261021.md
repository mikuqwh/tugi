# 「万能格式转换」与大工具台 — 方案（2026-10-21）

> 目标（用户原话）：做一个「万能格式转换」，支持绝大部分图片/视频格式，含视频转音频；
> 以 [T8RIN/ImageToolbox](https://github.com/T8RIN/ImageToolbox) 的功能面为参考，
> 在它之上叠加我们已有的 GIF 能力，做成一个更全能的图片编辑器。
>
> 本文只做规划，不改代码。所有「能/不能」都基于**本机模拟器上的实测**，不是猜的。

---

## 一、先说结论

1. **能做，而且大部分不用新依赖**：设备上的 ffmpeg 是 `full-gpl` / `n8.1.2`，图片 17 种输出格式、音频 7 种、
   视频 5 种容器已逐个实测通过（表在 §3）。
2. **有三个格式这个 ffmpeg 建不出来**：HEIC（写入）、JPEG XL（读+写）、动画 WebP 的往返。
   要补必须引原生库（libheif / libjxl），这是唯一的硬缺口，需要你决定要不要。
3. **视频转音频是最便宜的一刀**：`-vn -c:a copy` 在设备上实测 rc=0（2 s 视频 → 18.8 KB m4a），
   连重编码都不用，可以当天落地。
4. **「对标 ImageToolbox 全部功能」不是一个可信的承诺**：它有 310 个可链式滤镜、95 个 AI 模型、
   100+ 加密算法、OCR/PDF/条码/拼图/去背景……那是几年量级。建议按「转换器 → 图片工具台 → 精选编辑能力」
   三段推进，先把转换做到「真·万能」，再谈对标。

## 二、参考项目拆解（ImageToolbox）

来源：官方 README + [GIGAZINE 实机评测](https://gigazine.net/gsc_news/en/20260301-image-toolbox/)
（它按 Tab 组织：Edit / Create / Image / Tools）。

| 类别 | 它的能力 | 我们的现状 | 备注 |
|---|---|---|---|
| 格式转换 | JPG/PNG/WEBP/AVIF/HEIC/JXL/BMP/JPEG2000/TIFF/QOI/ICO/GIF，可调压缩类型/背景色/质量 | 无（本方案要做的） | 我们实测能覆盖其中 11/12；HEIC/JXL 缺 |
| 批量 | 批量处理、批量压缩、批量转换 | 无统一队列 | 需要先有共享任务队列 |
| 尺寸 | 裁剪、限制缩放、按 KB 压到目标体积 | Edit Image 已有压缩目标 | 可直接复用 |
| 滤镜 | 310 种可链式 + 模板滤镜 | Edit Image 有基础调节（亮度/对比/锐化等） | 不做全量；建议 LUT + 30 个常用项 |
| 绘制/文字/贴纸 | 绘制、Markup 图层 | 水印屏已有「多图层 + 拖动」雏形 | 可泛化成标注编辑器 |
| EXIF | 编辑/删除 | 无 | 中等工作量 |
| OCR / PDF / 条码 | ML Kit OCR、PDF 工具、扫码 | 无 | 都要新依赖 |
| 去背景 | 有 | 有 `matting` 模块（历史遗留，未接 UI） | 可评估复活 |
| GIF 工具 | 有独立 GIF Tools（很浅） | **我们 7 个 GIF 功能更深**（抽帧/压缩/编辑/水印/互转） | 这是我们的差异点 |
| AI | 95 个模型 | 无 | 明确不做（体积/算力/审核成本） |

**产品定位建议**：不追求功能数量对标，打「GIF 最强 + 格式转换最全 + 常用图片工具顺手」这三点。

## 三、实测能力矩阵（emulator-5554，ffmpeg-kit full-gpl，ffmpeg n8.1.2）

### 3.1 图片输出（逐个真跑，rc=0 才算数）

| 格式 | 命令要点 | 结果 | 备注 |
|---|---|---|---|
| PNG | `..*.png` | ✅ 174 B | |
| JPEG | `-q:v 3` | ✅ 248 B | 透明底要垫背景色 |
| WebP（静图） | `-c:v libwebp -quality 80` | ✅ 94 B | 支持透明 |
| **AVIF** | `-c:v libaom-av1 -cpu-used 8` + avif muxer | ✅ 326 B | muxer 存在；**慢**（AV1），要提示 |
| GIF | `..*.gif` | ✅ 1031 B | |
| APNG | `-f apng`（显式！） | ✅ 6737 B | 用 `.png` 后缀会走 image2，只出单帧 |
| BMP | `..*.bmp` | ✅ 12 KB | |
| TIFF | `..*.tiff` | ✅ 5.4 KB | |
| JPEG 2000 | `-c:v jpeg2000` → `.jp2` | ✅ 264 B | |
| QOI | `..*.qoi` | ✅ 91 B | |
| ICO | `..*.ico` | ✅ 12.9 KB | 多尺寸需另拼 |
| TGA / PCX / EXR / PAM / XBM / PPM | 直接写 | ✅ 全通过 | 小众但免费 |

### 3.2 图片输入（解码器存在性 + 后续矩阵验证）

有解码器：png/apng、jpeg、webp、avif(av1)、bmp、tiff、gif、jpeg2000、qoi、pcx、psd、exr、hdr、dds。
**无**：jxl/jpegxl（只有 `jpegxl_pipe` 解复用器，没有解码器）、heic/heif。

### 3.3 音频输出（从合成 2 s 正弦测）

| 格式 | 结果 | 备注 |
|---|---|---|
| MP3（libmp3lame） | ✅ 16.5 KB | `-q:a 2` |
| M4A / AAC | ✅ 18.7 KB | |
| FLAC | ✅ 32.4 KB | 无损 |
| OGG（vorbis） | ✅ 6.9 KB | |
| Opus | ✅ 18 KB | |
| WAV（pcm_s16le） | ✅ 176 KB | |
| AC3 / EAC3 / MP2 / WavPack | 有编码器 | 不建议出现在 UI |

### 3.4 视频→音频（用户明确要的功能）

实测 mp4（h264+aac）→ 四种音频全部 rc=0：

| 目标 | 方式 | 结果 |
|---|---|---|
| m4a | `-vn -c:a copy`（**不重编码**） | ✅ 18.8 KB，几乎瞬时 |
| mp3 | `-vn -c:a libmp3lame -q:a 2` | ✅ 11.0 KB |
| flac | `-vn -c:a flac` | ✅ 107.6 KB |
| wav | `-vn -c:a pcm_s16le` | ✅ 178.3 KB |

### 3.5 视频容器输出

| 容器/编码 | 结果 | 备注 |
|---|---|---|
| MP4 / H.264 | ✅ 12.6 KB | 主力 |
| MP4 / H.265 | ✅ 12.5 KB | 需 `-tag:v hvc1` 才能被 iOS/相册识别 |
| WebM / VP9 | ✅ 10.5 KB | |
| MKV | ✅ 12.3 KB | |
| MOV | ✅ 12.6 KB | |
| AVI / MJPEG | ✅ 71.9 KB | 兼容用途 |

另有 `h264_mediacodec` / `hevc_mediacodec`：**硬件编码器**可用，大视频转码应优先走它们（速度快数倍、发热低）。

## 四、技术方案

### 4.1 架构（沿用现有三层纪律）

```
lib/convert/
  format_registry.dart   纯数据：每个格式的 ext / mime / kind / 编码参数 / 是否支持透明 / 质量旋钮 / 预估模型
  capability_probe.dart  启动时用 ffmpeg -encoders/-muxers 校验注册表（不同 ffmpeg-kit 包会缺东西）
  convert_service.dart   批量编排：选参 → 构命令 → 跑 → 落盘 → 清理；复用现有 Gal/Share
  job_queue.dart         串行队列 + 进度 + 取消 + 失败重试（所有转换功能共用）
lib/ffmpeg/commands.dart 新增 convertImage / convertAudio / convertVideo（纯命令构建，无 IO）
lib/screens/format_convert_screen.dart
```

三条命令路径：

1. **图片**：`-i src -frames:v 1 [-vf ...] [-c:v encoder] [-q:v n] out.ext`
   - 透明→有损（JPEG/BMP）：自动垫白底（可调），或提示「将丢失透明」。
   - 多帧输入（GIF/APNG/WebP-anim）→ 静图：取首帧（明确提示）。
2. **音频/提取**：`-i src [-vn] -c:a <enc> [-q:a n] out.ext`
   - 若能 `copy`（容器兼容）就走 copy：**零质量损失 + 秒级**。
3. **视频**：`-i src -c:v <enc> -c:a aac [-crf/-b:v] [-vf scale/fps] out.ext`
   - 默认 `libx264 crf 23`；大文件提示可切 `h264_mediacodec`（硬编，质量略降但快）。

关键点：**不自己维护「格式 × 格式」矩阵**，而是「源 → 中间语义（帧/音频流）→ 目标」，否则组合爆炸。

### 4.2 UI（一屏完成）

```
[选文件 / 拖入多选]  →  自动识别类型（图片/动图/视频/音频）
   源卡：缩略图 + 分辨率/时长/帧数 + 体积
   目标格式：网格（按当前源类型过滤可用项，不可用的置灰并说明原因）
   参数：质量/缩放（可选）/帧率（视频）/音频码率/背景色
   预计输出：区间（复用 size_estimate 的思路，按实测校准）
   [开始转换] → 队列进度 → 结果（存相册 / 分享 / 继续下一个）
```

### 4.3 大小预估的真实性

已有校准方法论（`tool/wmprobe/calibrate_compress.sh`）。转换场景比压缩更难预测：
- 图片：`输出 ≈ 像素 × bpp(格式, 质量)`，bpp 可实测标定（每种格式每个质量档跑一张样图）。
- 音频：码率 × 时长，几乎精确（`-b:a 192k` → 1 分钟 ≈ 1.4 MB）。
- 视频：CRF 模式下不可预测（实测同素材 8 倍差距），只能给区间或只在「指定码率/目标体积」时给数字。

**结论**：图片/音频给数字，视频给区间或「目标体积模式」（两遍编码逼近，这本来就是 ImageToolbox 的
「Resize to specified size」思路）。

### 4.4 三个缺口的补齐选项

| 格式 | 现状 | 选项 | 代价 |
|---|---|---|---|
| AVIF 输出 | ✅ 已可（libaom-av1） | — | 慢，UI 要提示 |
| **HEIC 读/写** | ✗ | (a) Android `ImageDecoder`(API 28+) 读；(b) `HeifWriter`(API 28+) 写；(c) 引 libheif | (a)+(b) 走平台通道，中等；只覆盖 Android |
| **JPEG XL** | ✗ | 引 `libjxl`（CMC 构建 ~3-5 MB/ABI） | 体积涨、要维护 JNI |
| 动画 WebP 往返 | 部分（单帧 ✅，多帧往返实测失败） | 用 `libwebp_anim` 调参 / 走 Android `ImageDecoder` | 小 |

建议：**P2 先做 HEIC 读写（平台通道），JXL 挂起**——JXL 在用户群里占比极低，而 HEIC 是 iPhone 照片。

### 4.5 许可与分发（必须提前决定）

- 现在打的是 `ffmpeg-kit full-gpl`（含 libx264/libx265），**因此整个 App 必须以 GPL 兼容方式分发**，
  上架 Google Play 会有问题。
- 可选路线：`lgpl` 版 + `h264_mediacodec`/`hevc_mediacodec` 做视频（Android 设备基本都支持），
  代价是老设备兜底与部分滤镜缺失。
- ImageToolbox 是 Apache-2.0：**可以借鉴设计与参数，不要直接复制其代码**（含资源）。

## 九、附：要不要为 JXL 新建一个干净的 Android 工程？

> 用户提问（2026-10-21）：不打算商业上架，纯开源自用，为了更好地接入 JXL，
> 是否应该新建一个干净的 Android 工程，只把格式转换核心移植过去？

### 9.1 结论：不该。JXL 不是换工程的理由。

JXL 在当前栈上有三条路，**没有一条需要换 UI 框架**：

| 路线 | 做法 | 成本 | 影响面 |
|---|---|---|---|
| A. 自建 ffmpeg（推荐） | 用 [ffmpeg-kit-next](https://github.com/arthenica/ffmpeg-kit-next) 的构建脚本加 `--enable-lib-libjxl`，产出自己的 AAR/插件替换现有包 | 搭 CI 建 5 个 ABI，1–2 天；之后跟随上游 | 命令层**零改动**，JXL 只是多两个编解码器 |
| B. 写 Flutter 插件 | Android 端 JNI + CMake 链接 libjxl，MethodChannel 暴露路径级 API | 2–3 天 | 只在图片编解码路径上多一个分支 |
| C. 换 Kotlin 工程 | 同样要写 JNI（Android 系统不支持 JXL） | 3–6 周才有今天的功能对等 | 丢掉 9 个功能、UI 体系、探针与设备测试 |

关键事实：

1. **Android 系统解码器至今不支持 JXL**（`ImageDecoder` 只认 JPEG/PNG/WebP/HEIF/AVIF），
   所以「换原生」并不能白拿 JXL——JNI 那层代码在 Kotlin 里和 Flutter 插件里几乎一样长。
2. **pub.dev 上没有 Android 可用的 JXL 插件**：[jxl_coder](https://pub.dev/packages/jxl_coder) 只支持
   macOS/iOS/Windows，且只做 JPEG↔JXL，与本需求无关。
3. **ffmpeg-kit-next 明确支持 `--enable-lib-libjxl`**（见其 [External Libraries wiki](https://github.com/arthenica/ffmpeg-kit-next/wiki/External-Libraries)），
   且 libjxl 属于非 GPL 库。我们当前用的 `ffmpeg_kit_flutter_new` 8 个变体里**都没有** libjxl，
   但只要换成自建包，JXL 就变成和 PNG 一样普通的一个 `-c:v libjxl`。
4. 「只移植格式转换核心」是幻觉：核心（注册表 + 命令构建 + 队列）本身只有 2–3k 行纯逻辑，
   但真正值钱的是已经跑通的 9 个功能 + 设计系统 + 探针/设备测试纪律——这些只能重写，不能移植。

### 9.2 什么时候换工程才是对的

三个触发条件，满足任意一个再考虑重写：

1. **目标是 F-Droid 级「纯自由软件构建链」**：F-Droid 收录 Flutter 应用是可行的，但引擎预编译造成的
   构建链摩擦明显大于 Kotlin+Compose。这是唯一真正站得住的「开源」理由。
2. **要做深水区原生图像处理**：HDR / ICC 色彩管理 / RAW / 宽色域 / GPU 管线。
   Flutter 的 `dart:ui` 图像栈偏 8-bit sRGB，这类需求会持续撞墙。
3. **决定 fork ImageToolbox 并合并它的 310 滤镜**：那是 Kotlin 工程，最终一定在 Kotlin 里做。

### 9.3 如果还是要换，正确的顺序是「先抽核，再换壳」

1. 现在就把转换核心抽成 **纯 Dart 包 `packages/format_core`**：格式注册表、能力模型、命令构建、
   体积预估、媒体探测——**不 import Flutter**。将来翻成 Kotlin 是逐文件翻译，不是重新设计。
2. 定义编解码器抽象（`JxlCodec` / `HeifCodec` 接口 + 空实现），让 UI 与命令层只依赖接口，
   这样 A/B/C 三条路线可以随时切换。
3. 只有在 9.2 的条件确认后，再开原生工程；那时你带着一份可移植的核心和一份已验证的需求清单。

### 9.4 两句话的操作建议

- **本周**：用 ffmpeg-kit-next 试建一个只比 `full` 多 `libjxl` 的包（路线 A），同时把 P0/P1 的
  转换核心按 §9.3 的形态落盘。JXL 这件事 2 天内就有确定答案，且不阻塞任何功能开发。
- **不要**为了 JXL 重写整个 App；JXL 是「多一个编解码器」，不是「一次架构迁移」。
